# Архитектура: оркестрация моделей

## Scope And Inputs

Входы: brief.md, AC1–AC8; существующие capability contracts, Runtime registry и native инструменты хоста. Реализация остается Markdown/JSON-контрактом Studio OS с TypeScript-проверками.

## Studio Delivery And Support Model

Ведущий агент отвечает за распределение, интеграцию, проверку и соблюдение процесса; исполнитель отвечает только за назначенную ограниченную работу.

## Technology Selection And Alternatives

Выбран существующий capability-механизм: `model-orchestration`. Собственный API-исполнитель исключен выбором пользователя. Фиксированный список моделей быстро устаревает; вместо него используются текущие сведения хоста. Новых зависимостей и отдельного Runtime не требуется.

## Components And Responsibilities

- Capability задает обнаружение среды, режимы исполнения, выбор моделей, ограничения, контракт задания и проверку результата.
- Architecture создает активный `orchestration-plan.md` рядом с архитектурой, включая компактный вариант для одной модели.
- Task Decomposition связывает назначения с `T<n>` и `AC<n>`, владельцами файлов и зависимостями.
- Development перепроверяет среду, выполняет задания, проверяет изменения и фиксирует фактические результаты.
- Project Memory хранит ссылку на план; детали и статусы находятся в плане и отчете, а не копируются в активный контекст.

## Data Ownership And Interfaces

`templates/orchestration-plan.md` определяет общую структуру: scope, источник сведений о хосте и моделях, выбранный режим, назначения, бюджет/лимиты, правила восстановления и журнал заданий. План изолирован в активном Work Item; для lifecycle используется `docs/orchestration-plan.md`. Идентификатор инструмента или задания хранится как непривилегированная строка, без ключей и машинных путей.

Поддерживаются три режима: `single-model`, `same-model-delegation`, `multi-model`. Последний требует подтвержденного выбора конкретных разрешенных моделей. Когда выбор недоступен, используется default/inherited хоста без выдуманной идентичности.

## Security And Privacy

Передавать минимальный контекст, scoped инструкции, evidence и acceptance criteria. Не копировать секреты и полный разговор. Делегирование не расширяет разрешения, не разрешает новых внешних получателей данных и не отменяет пользовательский выбор модели. Новые провайдеры и инструменты не устанавливаются автоматически.

## Reliability And Failure Handling

По умолчанию максимум два одновременно работающих исполнителя, максимум две попытки на задание суммарно по моделям, глубина делегирования один уровень. Более строгие ограничения хоста и пользователя имеют приоритет. Неизвестная денежная стоимость не превращается в денежный бюджет; неизвестные метрики отмечаются Unknown. Для жесткого денежного или токенного лимита без возможности его контролировать оптимизация через дополнительных исполнителей не запускается.

Пересекающиеся владельцы файлов и зависимости сериализуются. После возобновления проверяются незавершенные задания до нового запуска. Непроверенный ответ исполнителя не принимается; исправление, смена исполнителя и работа ведущей модели учитываются в общем ограничении попыток.

## Model Orchestration For This Work Item

Текущий host: Codex; native collaboration доступна. Идентичность реально унаследованной модели и точные токены не предоставлены результатами запуска — Unknown; отдельное переключение моделей для этого dogfood не заявляется. Выбран `same-model-delegation`: ведущий агент реализует policy/Architecture, второй — Task Decomposition/Development, третий — сценарии и структурные проверки. Независимый аудит интеграции выполняется после правок. Используются ограниченные задания с непересекающейся записью; стоимость Unknown, экономия не заявляется.

## Migration And Compatibility

Существующие проекты не обязаны проходить Architecture заново только ради оптимизации. Если активного плана нет, Development записывает компактный `single-model` план по текущему scope; существенное изменение стратегии либо неопределенные границы работы возвращаются в Architecture. Старые quality gates сохраняются.

## Testing Strategy And Quality Gates

Структурные проверки регистрации, потребителей, шаблона и дистрибуции; Runtime-сценарии неизвестной модели, отсутствия выбора, ограничений бюджета, конфликтов, отказов и возобновления. Обязательные команды: `npm run test:runner`, `npm run test:runtime:dry`, `npm run release:check`. Реальные behavioral trials между разными моделями отдельно не авторизованы и не подменяются dry-проверкой.

## Architecture Decisions And Risks

Решение локально этой фиче; canonical architecture и исторический v0.5 не переписываются до Release. Основной риск — выполнение инструкций зависит от host/model; контракт не является внешним принудительным scheduler. Поддержка хоста и экономия требуют отдельной фактической evidence.

## Development Handoff

Interface Design не требуется. Следующий выбранный этап — Task Decomposition, затем Development. Сохранить принятые standards, добавить один capability и шаблон, интегрировать три Runtime, progressive loading и отчеты, добавить проверки и краткое описание использования.

The studio model

You bring the intent. The studio owns the path.

You do not need to arrive with a stack, roadmap, or complete specification. Studio OS turns goals and constraints into accepted decisions, working increments, and evidence of what is actually ready.

01

Start anywhere

Bring a rough idea, an existing codebase, a feature, a bug, or a research question. Studio OS detects the kind of work before acting.

02

Work like a studio

Product discovery, research, planning, architecture, interface design, development, and verification stay connected by one project state.

03

Finish with evidence

A passing build is not called a finished product. Validation, QA, Product Outcome, and Release make readiness explicit before the studio claims completion.

  1. 01

    Idea / Interview

    You

    I need a web app for a mobile bicycle repair team. Customers request service, dispatch assigns jobs, and technicians update status. No payments in the first release.

    Studio OS

    I will treat this as a new product. First I need to confirm who books the work, how dispatch operates today, and what outcome would make the first milestone useful. I will not choose a stack or start implementation yet.

  2. 02

    Discovery / Briefing

    You

    Most requests arrive by phone. One dispatcher coordinates two technicians. The main problem is not knowing what is scheduled, active, or ready.

    Studio OS

    The first milestone should prove one complete loop: create a request, schedule it, assign a technician, and update its status. Customer self-service, route optimization, and payments remain outside this milestone.

    • Problem evidence
    • Market alternatives
    • Accepted scope
  3. 03

    Planning / Design

    You

    Keep it fast on a tablet. We will probably add customer booking later, so the first release should not block that path.

    Studio OS

    Recommended: a responsive operations-first web app with today's route, job details, and explicit status transitions. The roadmap, interface flows, architecture decision, and quality constraints now preserve the later booking path without building it early.

    • Milestone plan
    • Interface contract
    • Architecture decision
  4. 04

    Development / QA

    You

    Proceed with the accepted dispatch milestone.

    Studio OS

    The increment is implemented and automated checks pass. The product is still marked Not Ready until the dispatcher workflow is verified on desktop and tablet, and Product Outcome confirms that the visibility problem is actually solved.

    • Working increment
    • Test evidence
    • Explicit readiness state
  5. 05

    Outcome / Release

    You

    The dispatcher completed the route and status workflow on both target devices. The milestone solves the original visibility problem.

    Studio OS

    Product Outcome is accepted and release checks pass. Spoke is deployed. The repository retains the decisions, verification evidence, current product state, and the next-milestone backlog.

    • Accepted outcome
    • Release evidence
    • Next milestone

Interaction layer

Install

Add the studio to your agent.

Install the packaged plugin for Codex or Claude Code, or use the universal Bootstrap with another filesystem-capable agent.

Add the GitHub marketplace, then install Studio OS:

codex plugin marketplace add Aleksei2507/studio-os
codex plugin add studio-os@studio-os

Start a new Codex session, then use Use Studio OS with a product request.

Add the GitHub marketplace, install Studio OS, then reload plugins:

/plugin marketplace add Aleksei2507/studio-os
/plugin install studio-os@studio-os
/reload-plugins

Start with /studio-os:studio-os, then add your product request.

Download the latest release archive, verify its checksum, extract it, and give the agent this entry contract:

Read and follow <studio-os-root>/adapters/universal/BOOTSTRAP.md. Use Studio OS. I want to build...

The release archive contains the Runtime core. It does not require npm at runtime.

Questions

Before you install.

Does Studio OS write the product?

The host AI agent performs the work. Studio OS supplies the workflow, stage boundaries, decision contracts, standards, and quality gates that keep that work coherent.

Is it tied to Codex?

No. Codex and Claude Code have packaged adapters. Other agents with filesystem access can enter through the universal Bootstrap included in each release.

Will it replace an existing stack or design system?

Not by default. Brownfield onboarding records evidence from the current codebase and interface system so later stages can preserve or deliberately revise accepted constraints.

How is Studio OS different from BMAD?

They overlap in structured AI-assisted product delivery. BMAD is a broad agile framework with specialized agents and workflows from planning into implementation. Studio OS emphasizes a development studio operating model: inferred routing, one active Runtime, project-local decisions, and separate gates for code completion, product outcome, and release. It is not presented as a drop-in replacement.

Is it production-ready?

Studio OS is currently alpha software. Its contracts and regressions are actively evolving, so use versioned releases and review project decisions.

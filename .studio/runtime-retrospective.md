# Retrospective

## Executive Summary

Ретроспектива охватывает период с релиза v0.5.0 (2026-08-07) до релиза v0.6.0 (2026-08-13): Work Item `admin-panel-task-tracing` (Task Decomposition Runtime, Traceability ID, admin-панель) плюс сам цикл выпуска v0.6.0. Процесс дошёл до Release и был подтверждён пользователем на каждом публикационном шаге. Основная польза, которую отметил пользователь, — прозрачность рассуждений о том, что стоит делать, а что нет. Основная помеха — плотность технического языка в общении.

## Project Context

- Milestone: `v0.5 Distribution And Delivery Assurance` (выпущен) → пострелизный Work Item `2026-08-07-admin-panel-task-tracing` → релиз `v0.6.0`.
- Mode: Brownfield, Workflow: `work-item-feature`.
- Триггер Work Item: пользователь сравнил Studio OS с внутренним spec-driven инструментом `sp` и не увидел профита; Briefing зафиксировал два конкретных пробела (task-level декомпозиция/трассируемость, удобство чтения артефактов).

## Stages Completed

Work Item Intake → Briefing (Planning пропущена, зафиксирована причина) → Architecture → Task Decomposition → Development (5 инкрементов/дополнений) → Validation (×2, PASS) → QA (PASS) → Product Outcome (PASS, все AC verified) → Release (v0.6.0, опубликован).

Retrospective ранее не запускалась ни разу с начала проекта — это первый прогон.

## Objective Observations

- Дважды документация писалась на английском вместо сохранённого Project Language (Russian) — оба раза поймал пользователь, не автоматическая проверка. Итог: добавлен общий чек в `skill/core/INVARIANTS.md`.
- Scope admin-панели был расширен пользователем в процессе (не только этот checkout, но и установленные копии плагина) — потребовало переписать `server.ts` → `server.js` и ввести `--workspace`.
- Реальный баг (`isMainModule` ломался на symlink-пути) нашёлся только через ручное end-to-end тестирование, не через изначальный автотест.
- Реальный баг (`.gitattributes` `export-ignore` не переопределяется для вложенного пути при export-ignore родителя) нашёлся только при настоящем прогоне `release:build` в CI на первом теге `v0.6.0` — локально был прогнан только `release:check` (структурная проверка), не полная сборка архива, перед первым пушем тега.
- Пользователь ни разу не позволил закоммитить или запушить без явного подтверждения; один раз явный выбор между двумя вариантами (force-move тега vs v0.6.1) был вынесен пользователю через структурный вопрос.
- Один clarifying-вопрос ("тут?" — куда именно строить прототип) был отклонён пользователем, который затем задал не связанный с ним вопрос про релиз — сигнал, что вопрос пришёл не в той точке разговора.
- RC-гейт (manifest-driven, fail-closed) дважды за период поймал реальную проблему до публикации: carve-out admin-панели в манифесте и баг `.gitattributes`.

## User Feedback

1. **Что было самым полезным:** рассуждения о том, что стоит добавлять, а что нет (явно назвал пользователь) — например, разбор идей монетизации/дыр в трассируемости с честной оценкой рисков, а не только список "давайте сделаем всё".
2. **Что раздражало:** много непонятных слов. Пользователь хочет, чтобы объяснения понимал даже нетехнический человек.
3. **Что изменить:** пользователь не назвал конкретную вещь ("да тут вроде все ок") — явных дополнительных изменений не запросил.

## Friction Points

- Плотность технического жаргона в объяснениях мешала пользователю, даже когда сама работа шла гладко.
- Два раза потребовалось ручное вмешательство пользователя, чтобы поймать нарушение Project Language.
- Реальные баги (symlink, gitattributes) оба раза находились поздно — на этапе ручного/CI прогона, а не заранее автотестами.

## Helpful Behaviors

- Явное различение "что стоит делать" от "что не стоит делать" с аргументацией по каждому пункту — прямо названо пользователем как самое ценное.
- Fail-closed RC-гейт: структурная проверка манифеста поймала две реальные проблемы до того, как они дошли до пользователя или до публичного релиза.
- Явное подтверждение перед каждым необратимым/публичным действием (commit, push, tag, force-push) — процесс ни разу не продвинулся без согласия пользователя.
- Догфудинг нового Runtime (`task-decomposition`) на том же Work Item, который его создал, прошёл без проблем.

## Repeated Issues

- Нарушение Project Language (английский вместо русского) — повторилось дважды в рамках одного Work Item, прежде чем было закрыто системным правилом.
- Расхождение между "структурная проверка прошла" (`--dry`/`--check`) и "реальная сборка прошла" (`release:build`) — источник обеих находок с багами в этой сессии.

## Candidate Improvements

- Объяснения и статус-обновления для пользователя используют слишком много технического жаргона без перевода на простой язык — кандидат для Evolution: упрощать формулировки по умолчанию, особенно в статусах/итогах, рассчитанных на нетехнического читателя.
- Нет автоматической проверки Project Language в момент записи (полагались на INVARIANTS.md как prose-правило, которое дважды не сработало до того, как было явно добавлено).
- `release:check` (структурный, `--dry`-подобный) и `release:build` (реальная сборка) можно спутать как "уже проверено" — кандидат: явнее развести в `RELEASING.md`, что именно каждая команда гарантирует.

## Notes For Evolution

Явного запроса пользователя на немедленные изменения нет ("да тут вроде все ок" на третий вопрос). Единственный явно названный кандидат — упрощение языка объяснений. Evolution должна сама решить, превращать ли это и остальные Candidate Improvements в proposals; Retrospective этого не предлагает.
